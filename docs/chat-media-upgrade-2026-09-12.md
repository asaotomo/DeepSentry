# 聊天附件链路改进（2026-09-12）

本轮在工作区已有聊天、图片输入、chat_send_file 和持久化文本 outbox 基础上继续实现。没有提交或覆盖其他 Agent、MCP、TUI 的既有改动。

## 能力

| 渠道 | 接收图片/文件 | 发图片/文件 |
| --- | --- | --- |
| QQ 原生 Bot | 复用已有附件入口及视觉模型输入 | 复用已有上传；新增持久化投递 |
| 微信 iLink | 复用已有下载、解密和引用附件解析 | 复用已有加密上传；新增持久化投递 |
| 企业微信长连接 | 复用已有图片/混合消息/文件解密 | 新增 init → chunk → finish 素材上传，512 KiB 分片，确认素材 ID 后发送 |
| 企业微信应用 | 已解析 image/file/voice，按 MediaId 下载 | 新增临时素材上传与应用消息发送 |
| 飞书回调及长连接 | 新增 image、file、audio、post 统一解析，授权任务内使用消息资源 API 下载 | 新增图片/文件 multipart 上传和消息发送 |

飞书图片进入真实视觉附件清单；图文保留标题、正文、链接和内嵌图片，多语言选择一份内容。语音仍需配置现有转写服务，图片理解仍需模型支持视觉。企业微信超过 2 MiB 的图片按普通文件发送。通用附件限制仍是单个 20 MiB、入站单条最多 8 个、累计 40 MiB。

## 文件投递与存储

- `chat_send_file` 使用原子发布，不再覆盖同名排队文件；第二个同名文件保留为 `名称 (1).扩展名`。隐藏文件名和 `.sent` 后缀不再被发送扫描器无声忽略。
- 同一条消息内的同名入站附件使用独立子目录保存，保留原文件名与各自视觉清单路径。
- 任务结束后先把待发送文件复制到 `<chat.store>.outbox/files/`，保存投递记录后才清理任务临时目录。发送扫描不再静默丢掉第九个及后续出站文件。
- 文件复用文本 outbox 的账号与接收者授权复核、会话串行投递、HTTP 限流退避、结果未知状态和重启恢复。`/delivery` 展示文件名及状态；`/retry 投递ID` 重试未确认部分，不重新运行 Agent。
- “已排队”不等于“已送达”。网络写入后缺少最终回执时不自动重发；人工重试结果未知的文件可能重复。上传与真正发送分开，上传拿不到资源 ID 时不会发送空附件。
- 已送达且超过七天的 outbox 记录，在启动清理时同步清理对应文件。失败及结果未知文件保留以供重试。
- 飞书凭据不进入附件模型；资源下载不跟随重定向。普通外部附件仍使用现有 HTTPS/地址限制；下载失败日志不再记录带签名的完整 URL。

## 验证与限制

新增回归覆盖飞书图文/文件解析、鉴权资源下载、同名图片路径、multipart 上传发送、企微跨分片上传和回执、文件清理后重启恢复、上传限流重试及不重复发送、重复文件名保留。使用本地 HTTP/WebSocket 模拟，不向真实聊天账号发送消息。

仍需真实账号验证机器人权限与平台配额。入站附件会在任务入队后预取；视频理解、SILK 解码和逐 token 卡片更新仍未实现。
